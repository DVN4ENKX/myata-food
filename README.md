# Myata Food

Система управления рестораном: QR-меню для гостей, загрузка зала, кухня, брони, отчёты, персонал и обмен с 1С:УНФ.

- **Backend** — FastAPI + SQLAlchemy 2 + Alembic, PostgreSQL (или SQLite для быстрого запуска)
- **Frontend** — React 18 + TypeScript + Vite, без UI-библиотек
- **Realtime** — WebSocket-каналы зала и кухни

## Быстрый старт

Требуется Docker с плагином Compose.

```bash
cp .env.example .env      # при необходимости поменяйте SECRET_KEY и пароли БД
docker compose up --build
```

Поднимаются три сервиса:

| Сервис | Порт | Назначение |
|--------|------|------------|
| `web`  | 5173 | nginx: статика SPA + проксирование `/api`, `/static`, `/health` |
| `api`  | 8000 | FastAPI |
| `db`   | 5432 | PostgreSQL 16 |

Откройте <http://localhost:5173>. Схема БД создаётся миграциями при старте
(`alembic upgrade head`), демо-меню засеивается автоматически, если база пуста.

> `PUBLIC_BASE_URL` должен указывать на адрес, по которому гости открывают QR-код.
> В docker-compose это `http://localhost:5173` — именно он зашивается в QR-коды.

Остановить: `docker compose down`. Удалить вместе с данными: `docker compose down -v`.

## Локальная разработка

Нужен Python 3.11+ и Node.js 20+.

### Backend

```powershell
cd backend
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -e ".[dev]"

Copy-Item ..\.env.example .env      # затем переключите DATABASE_URL на sqlite
.\.venv\Scripts\python.exe -m alembic upgrade head
.\.venv\Scripts\python.exe -m uvicorn app.main:app --reload --port 8000
```

При старте API:

- для SQLite схема создаётся сама через `create_all`, миграции можно не запускать;
- для PostgreSQL миграции обязательны — lifespan вызывает только `seed_if_empty`;
- если база пуста, выполняется `seed_if_empty`: демо-меню, залы, столы, пользователи;
- создаются каталоги `storage/images` и `storage/exports`.

Документация API: <http://localhost:8000/docs>, схема: <http://localhost:8000/openapi.json>.

### Frontend

```powershell
cd frontend
npm install
npm run dev            # http://localhost:5173
```

Порт 5173 в dev проксируется на `:8000` (`/api` с `ws: true`, `/static`, `/health`),
поэтому фронтенд и API работают на одном origin и CORS в dev не мешает.

Полезные команды:

```bash
npm run build          # tsc -b && vite build -> dist/
npm run preview        # отдать собранный dist на :4173 с тем же прокси
npm run typecheck      # только проверка типов
```

## Роли и права

Четыре роли и пять независимых флагов. Роль задаёт значения флагов по умолчанию,
их можно переопределить для конкретного сотрудника.

| Роль | menu | hall | orders | users | reports |
|------|:----:|:----:|:------:|:-----:|:-------:|
| owner | ✓ | ✓ | ✓ | ✓ | ✓ |
| admin | ✓ | ✓ | ✓ | ✓ | ✓ |
| manager | ✓ | ✓ | ✓ | — | ✓ |
| waiter | — | — | ✓ | — | — |

Что это значит на практике:

- **waiter** работает с залом: видит загрузку, столы, QR, брони, меню, кухню;
  сажает и закрывает гостей, двигает заказы по статусам. Не видит деньги
  (отчёты, выручка, аудит, 1С) и не может править меню или схему зала.
  В интерфейсе зал открывается в режиме «только чтение».
- **manager** дополнительно редактирует меню, модификаторы, категории, столы, брони,
  видит отчёты. Не управляет сотрудниками.
- **owner / admin** — полный доступ.

Операционные чтения (`/admin/occupancy/board`, `/admin/hall/*`, `/admin/orders*`,
`/admin/menu/*` на чтение, брони) доступны, если есть **хотя бы один** флаг из
`can_manage_orders`, `can_manage_hall`, `can_view_reports` — иначе официант не смог бы
работать со столом. Денежные отчёты и аудит по-прежнему требуют именно `can_view_reports`.

## Возможности

**Гостю по QR**

- меню с категориями и вложенными подкатегориями, поиск, модификаторы;
- корзина с комментарием к позиции, отправка заказа, список своих заказов;
- сервер пересчитывает цены: присланные клиентом цена и название модификатора
  игнорируются, неизвестные `modifier_id` отбрасываются;
- заказ без посадки отклоняется с `409` — гость должен быть заселён.

**Зал и посадка**

- визуальная схема зала, перетаскивание столов, сохранение раскладки;
- посадка, смена количества гостей, комментарий, закрытие стола;
- QR-код стола: SVG, PNG, матрица, лист со всеми столами, регенерация;
- автоматический подбор стола под бронь.

**Кухня и заказы**

- доска заказов с временем ожидания, статусы `new → in_progress → ready → served`;
- добавление позиций в открытый заказ, снятие позиций, отмена, скидка;
- пересчёт итога сервером.

**Меню**

- блюда: цена, вес, калории, аллергены, теги, время приготовления, фото, стоп-лист;
- категории с деревом и сортировкой, группы модификаторов, ограничения по блюдам;
- массовая доступность, настройки меню для гостя, статистика.

**Отчёты**

- дневной отчёт: выручка, заказы, средний чек, по источникам, по часам;
- отчёт по сотрудникам, закрытие дня, аудит действий.

**Прочее**

- сотрудники: роли, флаги, PIN, сброс пароля, блокировка;
- загрузка изображений (jpeg/png/webp/gif/avif) с проверкой типа и лимита размера;
- обмен с 1С: экспорт, импорт, журнал, карты соответствия.

## API

Префикс — `/api`. Всего **90 эндпоинтов**, OpenAPI 3.1.

Группы:

| Префикс | Назначение |
|---------|-----------|
| `/api/auth` | вход (пароль/PIN), профиль, смена пароля, роли |
| `/api/public` | меню и заказы гостя по QR-токену |
| `/api/admin/menu` | блюда, категории, модификаторы, настройки, статистика |
| `/api/admin/hall` | залы, столы, раскладка, QR |
| `/api/admin/occupancy` | загрузка, посадка, сессии, брони, отчёты |
| `/api/admin/orders` | заказы, кухонная доска, статусы, позиции |
| `/api/admin/users` | сотрудники, права, аудит |
| `/api/admin/upload` | загрузка и удаление изображений |
| `/api/admin/integration/1c` | настройки, экспорт, импорт, журнал |
| `/api/ws` | WebSocket-каналы |
| `/health` | проверка живости и БД (без префикса) |

Аутентификация — `Authorization: Bearer <access_token>`.

## WebSocket

| Канал | Назначение |
|-------|-----------|
| `/api/ws/occupancy` | загрузка зала, посадки, статусы столов |
| `/api/ws/kitchen` | новые заказы и смена статусов |

Подключение: `ws://<host>/api/ws/occupancy?token=<JWT>`.
Токен обязателен: сервер отклоняет недействительные и деактивированные учётные записи.

Клиент шлёт `ping` каждые 25 секунд, обрывает соединение при отсутствии ответа
и переподключается с задержкой. Рендер на `5173` и через nginx сохраняет апгрейд —
в `nginx.conf` для этого стоит `^~` на префиксе `/api/`.

## QR-коды

- токен стола — 16 случайных символов, ссылка `{PUBLIC_BASE_URL}/t/{token}`;
- PNG и SVG строятся сервером библиотекой `segno`, без внешних сервисов;
- ссылка приходит в поле `qr_url` вместе с `qr_token`;
- есть предпросмотр, лист всех столов и регенерация токена.

Картинки хранятся в `storage/images` и раздаются по `/static/<имя>` (в проде nginx
проксирует этот префикс на API).

## Обмен с 1С

Формат — XML, обмен через веб-сервис или выгрузку файлов.

- экспорт каталога (категории, блюда, модификаторы), заказов, закрытий дня;
- импорт номенклатуры с идемпотентностью по `external_id` и карте соответствий
  в таблице `sync_map` (уникальность на `(entity_type, local_id)` и
  `(entity_type, external_id)`);
- журнал обменов с количеством сущностей и превью payload;
- необязательная автовыгрузка по расписанию (`auto_export_interval_minutes`).

Реальный сервис 1С в тестах не используется — проверены только генерация,
разбор и идемпотентность обмена.

## Тесты

Тесты — standalone-скрипты, которым нужен **запущенный сервер**. Pytest их не
собирает (`python_files = ["test_*.py"]` в `pyproject.toml`): каждый скрипт сам
печатает `PASS/FAIL` и завершается с ненулевым кодом при ошибке.

```powershell
cd backend
.\.venv\Scripts\python.exe tests\reset_dev.py      # чистая БД + запуск API
.\.venv\Scripts\python.exe tests\smoke_test.py
```

Скрипт принимает базовый URL, поэтому проверяется и напрямую, и через прокси:

```powershell
.\.venv\Scripts\python.exe tests\smoke_test.py http://localhost:5173
```

| Скрипт | Проверок | Что проверяет |
|--------|:--------:|---------------|
| `smoke_test.py` | 113 | весь REST-периметр по ролям |
| `ws_test.py` | 11 | оба WebSocket-канала |
| `contract_test.py` | 54–55 | ключи и типы ответов, которые читает фронтенд |
| `frontend_flow_test.py` | 44 | сценарии гостя и официанта из UI |
| `upload_test.py` | 17 | загрузка, выдача и удаление изображений |
| **Итого** | **239–240** | |

Прогонялось и на SQLite, и на PostgreSQL через nginx — везде полный зелёный результат.
Разница между движками отсутствует: количество проверок зависит не от СУБД, а от
наличия данных, потому что часть проверок в `contract_test.py` вложена в
`if <есть заказы/сессии>:`. На чистой базе с одним только сидом их 55.

Тесты **не требуют сброса базы между прогонами** (логины, внешние ID 1С и столы
выбираются уникальными или свободными), но `reset_dev.py` перед прогоном удобен.

Линтер:

```powershell
.\.venv\Scripts\python.exe -m ruff check app tests
```

## Важные соглашения

**Деньги.** Цены блюд, модификаторов и отчётов хранятся **в копейках** (целые).
Итог заказа и позиции — **в рублях** (`Decimal`). Путаница этих единиц уже
закрывалась: `total_amount` суммировался в копейках, из-за чего был в 100 раз
больше суммы строк. Тесты проверяют, что `total_amount` совпадает с суммой
`line_total` и что модификаторы применяются **на единицу**, а не на строку.

**Модификаторы применяются на единицу позиции**: две шаурмы с доп сыром — это
`(цена + допы) × 2`. Формула согласована между `create_order`, `recalc_total`,
`order_read` и свойством `OrderItem.line_total`; расхождение между ними ломало
выручку в отчёте по сотрудникам.

**Деньги считает сервер.** Клиент присылает только `dish_id`, `quantity`,
`comment` и список `modifier_id`. Названия, цены и дельты берутся из БД.

**nginx и расширения.** Префиксы `/api/` и `/static/` объявлены как `^~`:
регулярные выражения в nginx проверяются раньше обычных префиксов, и без `^~`
запрос вида `/api/.../qr.png` обслуживался бы из файловой системы nginx и
возвращал 404. Затрагивает и QR-PNG, и картинки блюд.

**UUID.** Идентификаторы — UUID; в `SyncMap` и других местах нельзя полагаться
на `MIN(uuid)`: в PostgreSQL такой функции нет, и запрос падает. Дедупликация
выполняется через ORM.

**Иконка вкладки и шрифты** подключаются локально, внешние CDN не используются.

**Корзина гостя привязана к столу** и лежит в `localStorage` под ключом
`myata.cart.<token>`. Общий ключ на все QR-коды приводил к тому, что, отсканировав
второй стол, гость видел позиции первого. `GuestMenu` поэтому оборачивает страницу
в компонент с `key={token}` — при смене стола страница перемонтируется вместе с
корзиной.

**Модификаторы.** При превышении `max_select` выбор не вытесняет предыдущий
молча — гость получает сообщение. Группа с `min_select > 0` открывается уже с
предвыбранными вариантами, иначе гость сразу получает ошибку при добавлении в
корзину.

## Решение проблем

**`/api/.../qr.png` возвращает 404 через nginx.** Убедитесь, что в `nginx.conf`
префикс `/api/` объявлен как `location ^~ /api/`, а не `location /api/`.

**Картинки блюд не отображаются.** Проверьте, что каталог `storage/images` доступен
процессу API и что `/static/` проксируется на API. Путь в `image_url` — это
`/static/<имя>`, без лишнего сегмента `images`.

**`function min(uuid) does not exist` при старте Postgres.** Проверьте, что
применена актуальная ревизия миграции `3cd448ea3044`: старая версия использовала
`MIN(id)` по UUID, что работает в SQLite, но не в PostgreSQL.

**Не создаются таблицы в PostgreSQL.** Схему создаёт `alembic upgrade head`,
а не lifespan (тот вызывает `create_all` только для SQLite). В docker-compose
миграция выполняется автоматически перед запуском uvicorn.

**Официант не видит загрузку зала.** У пользователя должен быть выставлен
`can_manage_orders` (или `can_manage_hall`, либо `can_view_reports`) —
операционные чтения требуют любого из этих флагов.

**Тесты не находят сервер.** Запустите `tests\reset_dev.py`: он пересоздаёт БД,
применяет миграции и поднимает API на `127.0.0.1:8000`.

**Ошибка подключения к базе.** Проверьте `DATABASE_URL` в `.env`: после работы с
docker-compose там может остаться строка под PostgreSQL, тогда как локально
нужен `sqlite:///./storage/myata.db`.
