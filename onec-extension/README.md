# Расширение 1С:УНФ «Myata» — обмен с web-приложением

Расширение конфигурации для 1С:УНФ (платформа 1С 8.3, режим совместимости 8.3.27).

Оно делает две вещи:

1. **Принимает** XML-пакеты от Myata: номенклатура, группы номенклатуры, модификаторы,
   столы, заказы клиентов и закрытия дня.
2. **Отправляет** обратно номенклатуру и группы номенклатуры с ценами и артикулами.

## Как устроено

| Объект | Назначение |
|---|---|
| `ОбменСMyata` (общий модуль, сервер) | Настройки, разбор входящего XML, отправка в Myata |
| `MyataExchange` (HTTP-сервис) | Точка входа: `POST /hs/MyataExchange/ПриёмСообщения` |
| `НастройкиОбменаMyata` (регистр сведений) | Адрес сервера, учётные данные, состав обмена |
| `ОбменСMyata` (регламентное задание) | Периодическая отправка номенклатуры |
| `ОбменСMyata` (роль) | Доступ к номенклатуре и ценам для обмена |
| `УправлениеОбменомСMyata` (управляемая форма) | Настройка, проверка связи, ручной запуск |

## Установка

1. Откройте базу в «Конфигураторе».
2. **Администрирование → Расширения → Добавить расширение**.
3. Укажите имя `Myata`, режим совместимости `8.3.27`, синоним «Обмен с Myata».
4. Добавьте объекты расширения — либо импортировав XML из `Configuration/ConfigurationExtension/Content/`,
   либо создав их вручную по таблице выше.
5. Вставьте модули из каталогов `CommonModules/`, `HTTPServices/`, `ScheduledJobs/`,
   `ManagedForms/` в одноимённые объекты расширения.
6. **Администрирование → Обновление базы данных**.
7. Включите расширение и назначьте роль `ОбменСMyata` пользователю, от имени которого
   будет работать обмен.

> Метаданные расширения в `Configuration/` подготовлены вручную по формату 1С 8.3 и
> не проверялись в Конфигураторе: на этой машине нет установленной базы УНФ.
> Если импорт объектов не пройдёт, создайте их штатными средствами Конфигуратора —
> состав и свойства описаны в таблице выше и в комментариях к каждому файлу.

## Настройка

Откройте форму настройки обмена и заполните:

| Поле | Значение |
|---|---|
| Адрес сервера | `https://myata.ru` (публикация 1С при этом должна быть доступна извне) |
| Логин Myata / Пароль Myata | Пользователь Myata с ролью **Отчёт** — только ему открыт приём данных |
| Проверять пароль сервиса | Включите, если в Myata задан логин/пароль для отправки в 1С |
| Логин/пароль веб-сервиса | Те же значения, что в поле «Логин» и «Пароль» настроек интеграции в Myata |
| Ограничить количество позиций | `0` — отправлять всё; при первой проверке удобно поставить `20` |

Нажмите **Проверить связь**, затем **Выполнить обмен сейчас**.

## Настройка на стороне Myata

В разделе «Интеграция → 1С» укажите:

- **Адрес веб-сервиса** — `http://<хост-публикации-1С>/<имя-публикации>/hs/MyataExchange/ПриёмСообщения`
- **Логин / Пароль** — если включена проверка пароля сервиса.
- Включите нужные флаги выгрузки: категории, блюда, модификаторы, заказы, закрытия дня.

Выгрузка с галочкой «Отправить в веб-сервис» сразу уходит в 1С. Без неё пакет
сохраняется в `backend/storage/exports/` — это резервный вариант.

Регламентная выгрузка Myata (настраивается интервалом в той же форме) отправляет
пакет автоматически, если указан адрес веб-сервиса.

## Формат обмена

**Myata → 1С.** `POST`, `Content-Type: application/xml; charset=utf-8`, basic-авторизация.

```xml
<СообщениеОбмена Версия="1.0" ПланОбмена="..." ОтправкаПриложения="0"
                 Ид="..." ДатаОтправки="2026-09-29T12:00:00">
  <Отправитель>1C</Отправитель>
  <Параметры Имя="Организация" Значение="..."/>
  <Группа Имя="Справочник.Номенклатура" Количество="41">
    <Номенклатура Ссылка="..." Код="..." Наименование="..."
                  Артикул="..." ЦенаНДС="350.00" ВидНДС="НДС20"
                  ВМеню="true" Доступно="true" ПоказыватьВQR="true">Описание</Номенклатура>
    <Номенклатура Ссылка="..." Наименование="Сироп ванильный"
                  ЦенаНДС="20.00" ВидНДС="НДС20" Услуга="true" Активен="true"/>
  </Группа>
  <Группа Имя="Документ.ЗаказПокупателя" Количество="1">
    <ЗаказПокупателя Ссылка="..." Номер="..." Дата="..." Статус="closed"
                  Источник="qr" Стол="..." Гостей="2" Клиент="..." Итого="1500.00">
      <Товар Наименование="..." Количество="2" Цена="750.00" Комментарий="">
        <Модификатор Наименование="..." Цена="50.00"/>
      </Товар>
    </ЗаказПокупателя>
  </Группа>
</СообщениеОбмена>
```

Группы: `Справочник.НоменклатураГруппы`, `Справочник.Номенклатура`,
`Справочник.Столы`, `Документ.ЗаказПокупателя`, `Отчет.ЗакрытиеДня`.
Пустые группы в сообщение не попадают.

Блюдо и модификатор лежат в одной группе: их различает признак `Услуга="true"`
у модификатора.

Ответ расширения — JSON со счётчиками: `dishes`, `services`, `groups_in`,
`orders`, `items`, `day_closes`, `tables`, `receipts`, `receipts_skipped`, `errors`.

## Чеки ККМ

По умолчанию расширение только считает заказы. Если в форме настроек
включён флаг «Создавать чеки ККМ», то для каждого заказа создаётся
**черновик** `Документ.ЧекККМ` — без проведения и без фискализации.

Состав реквизитов в разных версиях УНФ разный, поэтому расширение ищет
нужную табличную часть и реквизиты в runtime, по метаданным:

- табличная часть позиций: `Товары`, `ТоварыИУслуги`, `Строки`, `Позиции`,
  а если таких имён нет — первая часть с реквизитом `Номенклатура` или `Товар`;
- в ней реквизиты `Номенклатура`/`Товар`, `Количество`, `Цена`, `Сумма`;
- шапка: `Комментарий`, `Организация`, `Склад`, `Продавец`, `Валюта`.

Отсутствующие реквизиты просто пропускаются, лишних ошибок не возникает.

Позиции ищутся только среди **ранее загруженной** номенклатуры — чек никогда
не создаёт новые элементы справочника. Если номенклатура не найдена, строка
пропускается, а если не найдена ни одна — в ответ попадает ошибка.

Повторная загрузка того же заказа не создаёт второй чек: в `Комментарий`
пишется маркер `[Myata:<номер заказа>]`, по нему чек ищется запросом.

Какие статусы заказа порождают чек — настраивается списком через запятую
в «Статусы заказа для чека» (по умолчанию `closed,served`). Пустой список —
чек создаётся для любого статуса.

Если при записи чека не хватает обязательного реквизита, текст ошибки от
1С попадает в ответ и в журнал регистрации — по нему видно, чего не хватило.

**1С → Myata.** `POST /api/admin/integration/1c/push`, `Authorization: Bearer <token>`,
тело JSON. Токен получается через `POST /api/auth/login` из тех же настроек.

```json
{"items": [
  {"entity": "Справочник.Номенклатура", "external_id": "A-100",
   "name": "Латте", "price": 250.0, "is_available": true, "article": "A-100"},
  {"entity": "Справочник.НоменклатураГруппы", "external_id": "COFFEE",
   "name": "Кофе"}
]}
```

`external_id` — артикул, а если его нет, строка UUID. Повторная отправка того же
`external_id` обновляет существующий элемент, а не создаёт дубль.

## Проверка

Контракт зафиксирован тестом `backend/tests/onec_test.py` (89 проверок). Тест
исполняет те же правила чтения, что и модуль расширения, поэтому расхождение
в именах элементов и атрибутов сразу ломает сборку.

Проверить разбор вручную в 1С:

```bsl
Текст = "<СообщениеОбмена Ид=""1"" ПланОбмена=""П""><Отправитель>1C</Отправитель></СообщениеОбмена>";
ОбменСMyata.ПринятьСообщение(Текст);
```

## Журнал

Всё пишется в журнал регистрации с событием `Myata.ОбменС1С`:
`Администрирование → Сервисы → Журнал регистрации`.

## Ограничения

- Заказы и закрытия дня принимаются и считаются, но документы в 1С не создаются:
  это осознанно, чтобы обмен не подменял учёт. Добавление документов делается
  в `ЗаписатьЗаказ` и `ЗаписатьЗакрытиеДня` модуля `ОбменСMyata`.
- Признаки `ВМеню`, `Доступно`, `ПоказыватьВQR` записываются только если такие
  реквизиты есть в вашей сборке УНФ; иначе они молча пропускаются.
- Цены пишутся в регистр `ЦеныНоменклатуры` с видом цены «Основная цена продажи».
